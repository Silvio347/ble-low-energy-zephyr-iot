# ESP32 BLE MQTT Gateway

This ESP-IDF firmware turns an ESP32 into a BLE-to-MQTT gateway for a Nordic nRF54L15 sensor node. The gateway scans BLE legacy advertisements, filters manufacturer data by company ID and device ID, validates the 14-byte application payload checksum, estimates packet loss from the payload counter, and publishes JSON telemetry to HiveMQ.

## Requirements

- ESP-IDF with ESP32 support.
- ESP32 module with 4 MB flash. The included partition table is sized for this 4 MB layout with OTA support.
- A HiveMQ broker or HiveMQ Cloud cluster.

## Build

```sh
idf.py set-target esp32
idf.py build
```

Flash and monitor:

```sh
idf.py -p /dev/ttyUSB0 flash monitor
```

Adjust the serial port for your host. If you changed target, partition layout, or OTA state, use a full erase before flashing:

```sh
idf.py -p /dev/ttyUSB0 erase-flash flash monitor
```

## Private Default Configuration

The firmware can load local defaults from `config/default_config.h` when no configuration has been saved to NVS. That file is intentionally ignored by git.

Create it from the committed example:

```sh
cp config/default_config.example.h config/default_config.h
```

Then edit `config/default_config.h` with your private Wi-Fi, MQTT, and BLE defaults. The project still compiles if this private file does not exist; in that case, blank fallback defaults force the device into configuration AP mode.

## Configuration AP

If saved configuration is missing or invalid, or if station mode cannot connect within 30 seconds, the device starts an open AP:

- SSID: `ESP32-Gateway-Setup`
- URL: `http://192.168.4.1/`

The portal can edit:

- Wi-Fi SSID and password
- MQTT host, port, username, password, TLS setting, client ID, and base topic
- BLE company ID and target device ID

Saving configuration stores it in NVS and reboots into normal gateway mode.

To erase saved configuration, either use the portal reset button or hold GPIO0 low during boot.

## OTA Updates

The configuration portal includes a firmware upload field. Upload the application binary generated by ESP-IDF, usually:

```text
build/esp32_ble_mqtt_gateway.bin
```

The upload endpoint streams the binary through ESP-IDF OTA APIs, validates the image, sets the next boot partition, and reboots on success. The included `partitions.csv` is a 4 MB flash layout with no `factory` partition and two OTA app slots: `ota_0` at `0x20000` and `ota_1` after it. Each OTA slot is `1920K`, so the generated application binary must fit inside that size.

Current partition layout:

```csv
# Name,   Type, SubType, Offset,   Size,  Flags
nvs,      data, nvs,     0x9000,   24K,
otadata,  data, ota,     0xf000,   8K,
phy_init, data, phy,     0x11000,  4K,
ota_0,    app,  ota_0,   0x20000,  1920K,
ota_1,    app,  ota_1,            , 1920K,
```

Because there is no `factory` partition, initial flashing writes the application to `ota_0`. Keep `otadata` in the flash command or use `idf.py flash` so the bootloader selects the correct OTA slot.

## BLE Payload

Manufacturer data must start with a 2-byte Bluetooth company ID, followed by this 14-byte little-endian payload:

```c
typedef struct __attribute__((packed)) {
    uint16_t device_id;
    int16_t temperature_x10;
    uint16_t humidity_x10;
    uint16_t battery_mv;
    uint32_t counter;
    uint8_t flags;
    uint8_t checksum;
} sensor_payload_t;
```

The checksum is the sum of all payload bytes before `checksum`, truncated to 8 bits.

Flags:

```c
#define FLAG_SENSOR_OK        BIT(0)
#define FLAG_BATTERY_SIM      BIT(1)
#define FLAG_LOW_POWER_MODE   BIT(2)
#define FLAG_DHT_ERROR        BIT(3)
```

## MQTT

The gateway publishes to:

```text
{base_topic}/{device_id}/telemetry
```

With the default base topic, device `1` publishes to:

```text
lowble/1/telemetry
```

JSON schema:

```json
{
  "device_id": 1,
  "temperature_c": 24.7,
  "humidity_percent": 53.2,
  "battery_mv": 3010,
  "counter": 42,
  "flags": 1,
  "sensor_ok": true,
  "dht_error": false,
  "low_power_mode": false,
  "battery_simulated": false,
  "rssi": -63,
  "packet_loss_total": 0,
  "packet_loss_delta": 0,
  "checksum_valid": true,
  "timestamp_ms": 123456
}
```

HiveMQ Cloud normally uses TLS on port `8883` and requires username/password authentication. TLS mode uses the ESP-IDF certificate bundle.

## Troubleshooting

- If the configuration portal always starts, check that Wi-Fi SSID, MQTT host, port, client ID, and base topic are set.
- If MQTT does not connect, verify HiveMQ host, username, password, TLS mode, and port.
- If no BLE samples publish, verify the company ID byte order, target device ID, and that the Nordic node is using legacy advertising manufacturer data.
- If `checksum_valid` is false, compare the Nordic payload bytes with the checksum algorithm documented above.
- If OTA fails to start, verify that the custom 4 MB partition table is active and contains `ota_0`, `ota_1`, and `otadata`.
- If the image does not fit in the `1920K` OTA slot, reduce firmware size, disable unused features, or move to a board with larger flash and update `partitions.csv`.
